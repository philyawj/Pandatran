# Pandatran initial research

Research reviewed November 26, 2026.

**Can a chess engine written in a language introduced in 1957 beat our chess engine written in a language introduced in 2009?** IBM released Fortran commercially in 1957. Go was publicly released in 2009. Pandatran will be an original, modern Fortran engine. The test is whether it can beat the frozen Pandafish v1.0 under equal conditions. It measures the two finished engines under a specified protocol. Language, architecture, development model, and accumulated experience all differ. [IBM’s Fortran history](https://www.ibm.com/history/fortran) · [Go’s release history](https://go.dev/blog/12years)

| Engine | Language | Codex development model |
| --- | --- | --- |
| Pandafish | Go | **GPT-6.1-sol, high reasoning**, as reported by the project owner |
| Pandatran | Modern Fortran | **GPT-6.2-sol, high reasoning**, planned for development |

**Recommended approach.** Build the chess core in Fortran from scratch, use independent implementations as test oracles, and get into timed matches as soon as a simple search plays legal games. Pursue three levers in order of dependency: reliable position handling, efficient search, and better evaluation. Begin with a measurable classical engine. A compact NNUE becomes a candidate if match evidence and an inference-cost prototype justify the investment. Ten checkpoints are a useful structure. The tenth is a testable finish line, and the result could be decisive earlier or require more development.

## Fortran’s place in computer chess

Claude Shannon’s 1950 paper described the trade-off between broad search and selective search before Fortran was commercially available. The first World Computer Chess Championship followed in 1974. On the mainframes and supercomputers of the late 1970s and 1980s, Fortran was part of the competitive field. Tournament teams mixed high-level code with machine-specific kernels, and major algorithmic choices included how to order moves, reuse positions, and spend search effort. Fortran’s strongest documented appearances belong to that era. [Shannon’s paper](https://www.fermatslibrary.com/s/programming-a-computer-for-playing-chess) · [ICGA championship history](https://icga.org/icga/news/wccc/) · [1981 ACM tournament program](https://d1yx3ys82bpsa0.cloudfront.net/chess/1981-acm-naccc.062303017.pdf)

Cray Blitz won the 1983 and 1986 world championships. Nuchess was a Fortran rewrite of Northwestern’s Chess 4.9 lineage, which had won the 1977 championship. The later rewrite and its predecessor are distinct entries in the history. Specialist systems also advanced during this era, including Belle, which won in 1980, and eventually IBM’s Deep Blue, which defeated Garry Kasparov in 1997. Later, open development and large match-testing networks helped projects such as Stockfish iterate on software search and evaluation. Stockfish’s 2020 NNUE introduction brought efficiently updated learned evaluation into its CPU alpha-beta engine. That lineage makes modern techniques fair game for Pandatran. [1980 ACM program](https://d1yx3ys82bpsa0.cloudfront.net/chess/the-eleventh-acms-north-american-computer-chess-championship.1980.062303015.pdf) · [ICGA championship history](https://icga.org/icga/news/wccc/) · [IBM’s Deep Blue paper](https://research.ibm.com/publications/deep-blue) · [Stockfish’s NNUE announcement](https://stockfishchess.org/blog/2020/introducing-nnue-evaluation/)

## What Pandafish taught us about development

I inspected the local Pandafish checkout, its release tag and history, the benchmark workflow, and the archived investigations. This section uses those artifacts as evidence about **development decisions and experiments**. Pandatran’s board, move generator, search, evaluator, time manager, and UCI code will be designed independently.

| Observation from Pandafish | Process lesson for Pandatran |
| --- | --- |
| **End-to-end first.** v0.1 made legal moves and completed games on Lichess before it could play well. Time-aware, interruptible search arrived in v0.7. v0.8 made real games easier to diagnose. Later reporting work repaired partial search-to-game linkage. [History](https://github.com/philyawj/Pandafish/blob/v1.0/docs/HISTORY.md) | Get a legal timed game working early. | **The library got the first engine playing; the hot path later needed substantial ownership.** Pandafish v1.0 replaces its pinned `corentings/chess/v2` v2.6.1 dependency with an in-tree copy and additions for search. v0.17–v0.23 repeatedly profiled and specialized generation, state transitions, evaluation, ordering and exchange checks. ## Independent architecture and toolchain

**Use modern Fortran.** Fortran 2023 is the current ISO edition. Start with free-form modules and a Fortran 2018-compatible subset supported by the compilers we actually test, using Fortran 2023 features when support and a concrete benefit are verified. Use GNU Fortran as the first compiler, with separate debug and optimized builds. The current Apple silicon workstation has gfortran 14.1.0. Confirm macOS ARM64 locally and a Linux target before bot integration. Use Fortran Package Manager (fpm) for build and test targets, with a TOML manifest and no repository-owned build scripts in another language. [Fortran 2023 specification](https://www.iso.org/standard/82170.html) · [GNU Fortran standards](https://gcc.gnu.org/onlinedocs/gcc-14.2.0/gfortran/Standards.html) · [Fortran Package Manager](https://fpm.fortran-lang.org/)

- **Own position state and legality.** Start with 64-bit piece and occupancy bitboards, a square-to-piece map where it simplifies piece lookup, a compact integer move, and fixed-capacity buffers by ply. Keep derived state verifiable by recomputation. Use straightforward sliding attacks plus precomputed leaper attacks first. Keep a clear directional reference for differential checks and profile before choosing a lookup scheme. Test en passant that exposes check, castle transit squares, promotions, double check, and pinned pieces. Keep a simple legal-move path available for verifying optimized generation. [Bitboards](https://chessprogramming.org/Bitboards) · [Move generation](https://chessprogramming.org/Move_Generation) · [Perft reference positions](https://chessprogramming.org/Perft_Results) · [Cozy Chess perft examples](https://github.com/analog-hors/cozy-chess)
- **Use Fortran intrinsics and measure the generated code.** Use explicit integer kinds from `iso_fortran_env`, bit intrinsics such as `iand`, `ieor`, `popcnt` and `trailz`, and bounded arithmetic for scores and nodes. Treat bitboards as bit patterns. Avoid depending on signed overflow, implicit short-circuit evaluation, or expressions whose order changes side effects. Check compiler temporary diagnostics and profile before rearranging arrays. Keep recursive state lifetime explicit and allocation outside the node loop. [GNU Fortran intrinsic reference](https://gcc.gnu.org/onlinedocs/gfortran/Intrinsic-Procedures.html) · [GNU Fortran runtime checks](https://gcc.gnu.org/onlinedocs/gfortran/Code-Gen-Options.html)
- **Build a predictable search before adding selectivity.** Use iterative deepening over negamax alpha-beta, mate distance and a check-aware quiescence search. Add a transposition table with explicit bounds, depth and mate-score normalization, and order moves using hash moves, tactical quality and quiet history. Cover repetition and move-count context before reusing draw-sensitive scores. Add principal variation search and aspiration windows when the baseline is stable. Then test late move reductions and guarded null move as individual hypotheses, with full-depth re-search where appropriate and specific zugzwang, check and mate regressions. [Ethereal source](https://github.com/AndyGrant/Ethereal) · [Transposition tables](https://chessprogramming.org/Transposition_Table) · [Graph history interaction](https://chessprogramming.org/Graph_History_Interaction) · [Quiescence](https://chessprogramming.org/Quiescence_Search) · [Late move reductions](https://chessprogramming.org/Late_Move_Reductions) · [Null move pruning](https://chessprogramming.org/Null_Move_Pruning)
- **Start with evaluation that can be tuned and explained.** Use material and phase-interpolated piece-square tables as the first search evaluator. Evaluate candidate groups such as pawn structure, mobility, and king safety through small ablations. Consider Texel-style fitting on independently sourced positions. If that route stalls despite sound search, evaluate a compact, incrementally updated NNUE as a distinct experiment. Compare accumulator updates against full refresh, measure inference and search throughput, and validate at both clocks. Training tooling can be external. Include network and data provenance and licensing in the decision. [Tapered evaluation](https://chessprogramming.org/Tapered_Eval) · [Texel tuning](https://chessprogramming.org/Texel%27s_Tuning_Method) · [Stockfish NNUE](https://stockfishchess.org/blog/2020/introducing-nnue-evaluation/)

**Library choice.** Write board state, attacks, move generation, make/unmake, and search in Fortran. Existing Fortran projects are references. The test suite can compare against Stockfish perft externally and keep verified fixture data in-tree. Revisit this choice only if a specific verified library offers the right state ownership, reproducible legality, adequate profiling data, and compatible licensing. Opening books, engine tablebases, and multithreaded search can wait while we establish a robust single-core result. [Stockfish perft command source](https://github.com/official-stockfish/Stockfish/blob/master/src/uci.cpp)

**UCI is part of the engine contract.** Support `uci`, `isready`, `ucinewgame`, `position startpos|fen ... moves ...`, `go` with clocks, increment, movetime, depth and infinite mode, `stop`, and `quit`. Add `nodes` for deterministic probes and `searchmoves` for targeted diagnostics. Expose only working options. Emit legal `bestmove`, or `0000` for a terminal root, flush protocol output, and handle readiness while searching. Test stop-before-depth-one, repeated go/stop, position replacement, EOF, and process restarts over pipes. Keep pondering off in the match/client configuration initially. Prototype how commands reach an active search before layering on heuristics. If needed, use Fortran `iso_c_binding` interfaces to call the operating system’s POSIX polling and input routines directly on the supported targets. Keep stdin on one input path to avoid mixing runtime-buffered reads with descriptor reads. Prototype and test the bindings on macOS and Linux ARM64. The chess logic and UCI interpretation stay in Fortran. First exercise fastchess, then a pinned lichess-bot build and a casual smoke game when deployment is in scope. [Original UCI protocol](https://www.shredderchess.com/chess-features/uci-universal-chess-interface.html) · [fastchess compliance checker](https://github.com/Disservin/fastchess) · [lichess-bot](https://github.com/lichess-bot-devs/lichess-bot)

### The classical-first project brief

- **The performance premise is credible.** Fortran was designed for numerical and scientific computing and gfortran produces native executables. The language can express 64-bit bitboards and compact integer loops well. Measure the payoff on chess workloads, where branch behavior, memory access and search quality matter as much as arithmetic. Native compiler quality and architecture matter more to this project than the date on the language’s first release. [IBM’s Fortran history](https://www.ibm.com/history/fortran) · [GNU Fortran intrinsics](https://gcc.gnu.org/onlinedocs/gfortran/Intrinsic-Procedures.html)
- **Fortran is the repository’s only implementation language.** Keep the engine, tests, benchmarks and any project-owned helper programs in Fortran. Markdown, configuration manifests and fixture data support the project. Install external tools separately, and let them communicate with the engine over UCI. The engine should run without third-party chess libraries, weights, opening books or tablebases in the classical configuration. Verify deployment linkage against the target OS and compiler runtime before claiming a standalone package.
- **Start small, classical, and readable.** The initial engine uses a handcrafted mathematical evaluator and no neural network, embedded opening book or tablebase. An external runner’s neutral opening suite provides repeatable match starting positions. The broader experiment allows any search or evaluation technique, so a classical-only finish is a promising target, with NNUE available as a later evidence-driven decision. Keep brief public development notes explaining what was measured, what failed, and what was learned.
- **Target a Raspberry Pi for primary performance measurements.** Prefer a dedicated, cooled Pi running 64-bit Linux, with the exact board and OS pinned before calibration. Use the Apple silicon workstation for development and instrumented debugging. Record CPU model, core allocation, temperature and throttling, build versions and background load on the match host. Keep both sides on the same physical Pi for the headline result. The Pi model and actual availability remain to be confirmed. [Raspberry Pi hardware documentation](https://www.raspberrypi.com/documentation/computers/raspberry-pi.html) · [Raspberry Pi cooling guidance](https://pip-assets.raspberrypi.com/categories/685-app-notes-guides-whitepapers/documents/RP-003608-WP-3-Cooling%20a%20Raspberry%20Pi%20device.pdf)

The loop from the project notes illustrates the programming style. A real search also tracks the move that owns the score, position updates, bounds and cancellation.

```fortran
do i = 1, move_count
  score = evaluate(moves(i))
  best = max(best, score)
end do
```

## Strength testing and the frozen opponent

### The baseline and the fair-match contract

- **Freeze Pandafish v1.0**, commit `27a34937c2aaee23d6e22bf60cee9b0075c16ad6`. Prefer the published Linux ARM64 release asset for the Pi if it verifies and runs there. Record its actual SHA-256 and UCI identity. If building from source is necessary, use the exact tagged tree with the vendored module and pin the Go compiler and flags. The locally observed Go 1.24.5 is older than the repo’s Go 1.25 requirement. Neither the Pi binary nor fastchess was run during this research. [Pandafish v1.0 release](https://github.com/philyawj/Pandafish/releases/tag/v1.0) · [Pinned Go module](https://github.com/philyawj/Pandafish/blob/v1.0/go.mod)
- **Give both engines the same resources and clocks.** Use one search thread each, the same host class for development batches, and the same physical host for confirmation. Match defaults should disable pondering and engine books/tablebases. Pandafish has a fixed score table of about 2 MiB and a separate move-hint table of about 1 MiB. Cap Pandatran’s corresponding table/hash budget at approximately 3 MiB combined for the primary match. Set a separate common process-memory ceiling once measured on the Pi, and record observed peak RSS. Use native release builds and fix runner concurrency to a level that passes load and timeout checks. If changing the budget for an exploratory run, label that result separately. [Pandafish engine and cache sizes](https://github.com/philyawj/Pandafish/blob/v1.0/docs/ENGINE.md)
- **Use clocks that test full-game allocation.** A reasonable calibration starting point is `10+0.1` seconds for regular play and `60+0.6` for a longer checkpoint, subject to a Pi timing pilot. Choose and freeze the primary and secondary profiles before collecting confirmation data. Use the same time margin and adjudication settings for both sides. Play to rule endings where practical. Pin any move-cap policy in advance and report capped games, illegal moves, crashes and flags. Engine-caused failures count under the match rules. A host or runner incident gets an explicit record and any predeclared whole-pair recovery. A fixed-depth or fixed-node run is useful for diagnosis, and a short fixed-movetime run can preserve historical continuity. [fastchess options](https://github.com/Disservin/fastchess/blob/master/man.md)
- **Pair openings and freeze a holdout.** Play each starting position twice with colors reversed. Prefer a broad suite of distinct positions with reasonable diversity and recorded origin, license, hash and seed. Use separate development and confirmation suites. If a final sample repeats position families, predeclare how to aggregate or resample at the family level. Keep the final holdout out of evaluation training, negative-case mining and candidate selection. PGNs and pair-level outcomes should make the result reproducible. [Fishtest statistics](https://official-stockfish.github.io/docs/fishtest-wiki/Fishtest-Mathematics.html)
- **Use independent opponents for context.** Test candidate versus last accepted Pandatran for patch decisions. Run periodic matches against the frozen Pandafish for the project objective. Keep a small external reference, such as a pinned Sacrifice build or a fixed Stockfish version and difficulty, to detect opponent-specific changes. External scores add context. The headline claim comes from the direct match.

### From smoke test to a superiority claim

| Question | Measurement |
| --- | --- |
| Does it work? | Perft and move-set diffs, state/key round trips, deterministic search fixtures, protocol compliance, and a handful of timed color pairs. Repeat only to investigate a failure or check a fix. |
| Is a patch worth keeping? | For an exact rewrite, compare moves, scores, nodes and elapsed time on fixed workloads. For a strength change, use roughly 25–100 fresh pairs as a first screen for large effects, or define an SPRT for narrower effects. Fix the Elo model, hypotheses, error levels and a game/resource cap before launch. Reaching the cap without a verdict is inconclusive. |
| Has Pandatran beaten Pandafish? | Freeze one candidate and use a fresh fixed-size paired match on the Pi. Prespecify the analysis and publish score, W/D/L, five opening-pair outcome bins, forfeit counts, game count and a paired 95% confidence interval. Claim superiority at the primary clock when that interval’s lower score bound exceeds 50%. Report the longer control separately and use the same criterion if claiming superiority there as well. Elo may accompany the result as a match estimate with its interval and model. |

Use each opening pair as the sampling unit. Its score for Pandatran is the average of the two game scores, with possible values of 0, 0.25, 0.50, 0.75, and 1. For a planning example, if the pair-score standard deviation is 0.35, a normal approximation with a two-sided 95% interval and about 80% power gives roughly **400 pairs for a true 55% score**, or **1,100 pairs for a true 53% score**. Those are about 800 or 2,200 games, respectively. Use a separate calibration sample to estimate actual variance and duration before freezing a confirmation budget. The approximation assumes independent pairs and illustrates why a 50-game screen settles only large gaps. A close result is a valid outcome. [Fishtest paired and sequential statistics](https://official-stockfish.github.io/docs/fishtest-wiki/Fishtest-Mathematics.html)

### fastchess and OpenBench

**Start with fastchess.** It handles local UCI matches, repeat openings with swapped colors, concurrency, PGN output, a protocol compliance checker, and paired statistics and SPRT controls. Pin its version and test option syntax during checkpoint 1. A small run record is enough glue at first. Keep perft, deterministic engine benches, targeted regressions and PGN/manifest decisions as project-owned work. This replaces the tournament machinery that Pandafish hand-rolled while retaining its best experimental habits. [fastchess repository](https://github.com/Disservin/fastchess) · [Match option reference](https://github.com/Disservin/fastchess/blob/master/man.md)

**Use OpenBench once repeat patch testing or multiple workers justify it.** It is a language-agnostic UCI test service used by Ethereal, backed by Django and fastchess, and supports fixed-game and SPRT jobs. It adds coordinated workers and a central history. A pilot should verify that a private instance can build Pandatran through fpm on its workers, report an extractable deterministic node-count bench signature, and use the frozen Pandafish binary as the control if needed. Keep any runner-specific build adapter in the external worker configuration. Check worker platform and compiler discovery, opening access, bench-output parsing, and NPS-derived time scaling. The official match should retain identical unscaled wall clocks on one Pi. Validate those settings explicitly before using OpenBench output as headline evidence. [OpenBench](https://github.com/AndyGrant/OpenBench) · [Worker build and time scaling](https://github.com/AndyGrant/OpenBench/blob/master/Client/worker.py) · [Worker bench parsing](https://github.com/AndyGrant/OpenBench/blob/master/Client/bench.py)

## Ten development checkpoints

The checkpoints are acceptance gates. A gate can produce a working feature, a rejected experiment, or a decision to defer an optional method. The technical implementation plan can specify module interfaces, exact commands, sequencing within each checkpoint, and budgets after this review.

| # | Checkpoint | Evidence to move forward |
| --- | --- | --- |
| 1 | **Freeze the experiment and bootstrap Fortran.** Verify the target Pi and macOS compilers, fpm debug and release builds, pinned Pandafish and fastchess. Define the match record, choose a development opening set, reserve a holdout and run Pandafish self-play as a harness control. | A reproducible baseline build or authenticated release asset, complete legal paired PGNs, recorded clock/load behavior and a practical primary-clock proposal. |
| 2 | **Legal chess core.** Implement board state, FEN, attacks, moves and make/unmake, including special moves and reversible history. Keep the initial fast path inspectable. | Canonical perft and divide on multiple positions, matching legal move sets against an independent implementation, and full state/key restoration after deterministic random walks. |
| 3 | **First timed UCI games.** Add the protocol adapter, command handling during search, legal fallback, terminal handling, and a basic timed search with material and piece-square values. | Pipe and cancellation tests, fastchess compliance, and completed timed pairs against a reference and frozen Pandafish. Record the initial score and failure rates. |
| 4 | **Trustworthy tactical baseline.** Establish iterative deepening, alpha-beta, quiescence, draw handling and mate scores. Freeze deterministic bench positions and output. | Reproducible bench signature and expected outcomes for mate, no legal moves, en passant legality, repetition, move-count draws, dead material and check evasions. Search and runner agree on terminal cases. |
| 5 | **Cache and order efficiently.** Add Zobrist keys, a bounded transposition table and staged move ordering. ## Automate the development loop

**Default to executable checks and reserve GPT-6.2-sol high for work that needs judgment.** The routine loop should run from a terminal without an LLM session. Use fpm and external tools directly. Add a small Fortran helper only when a recurring manual step demonstrably wastes time or causes mistakes. This meets the Fortran-only rule while delivering the repeatability of scripts.

| Task | What runs without Codex | Where Codex adds value |
| --- | --- | --- |
| Build and validate | fpm builds and runs rule, perft, state, deterministic bench, and UCI fixture checks. Failures print the position, seed or command sequence and the first disagreement. | Design the initial invariants and diagnose novel failures that the fixtures expose. |
| Run experiments | A pinned fastchess command runs the recorded manifest. Save the command and runner output alongside a short manifest with versions, settings, opening seeds and artifact hashes. Repeat validation with the recorded inputs. | Select a hypothesis, choose guard positions, explain unexpected results, and decide whether a change merits another experiment. |
| Decide routine outcomes | Compare fixed-work outputs to their reference and apply explicitly encoded mechanical thresholds. Emit pass, fail, or inconclusive with the failed metric, the reproducer and links to full artifacts. | Interpret conflicting metrics, change the design or test when evidence warrants it, and decide whether the next change is worth the cost. |
| Record and resume | Use the runner’s own summary and preserve PGNs. Record interrupted runs and recover using runner capabilities and the paired-match policy. | Write a short public checkpoint note about what changed and what the result means. Make scope and promotion decisions from the summaries. |

Start with fpm targets, checked-in fixtures, documented fastchess commands, and the runner’s existing reports. Manual tagging and a short experiment record are enough until repeated runs show a specific bottleneck. A small Fortran report helper can pay off if gathering the same fields becomes tedious. Leave queueing and worker management to OpenBench if the project ever needs them.

Each implementation turn should get the accepted commit, one hypothesis, the acceptance command, the expected artifact and a compute budget. Keep a compact handoff with the latest direct gap, accepted test commands and adverse cases. Read summaries first and open the smallest relevant log excerpt when a run fails. Save both positive and negative decisions so later sessions can use the evidence without repeating a run or loading its full history.

For the implementation plan, the remaining calibration decisions are the exact Pi, pinned compiler and runner versions, the opening suites, and the match clocks and sample budget after the pilot. The working defaults are Fortran-only source, from-scratch engine core, classical-first evaluation, a single search thread, fastchess for matches, and the tagged Pandafish v1.0 as the fixed opponent.
